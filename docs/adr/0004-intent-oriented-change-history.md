# ADR 0004: 変更情報をHow・What・Why・Why notへ分離する

- Status: Accepted
- Date: 2026-07-26

## Context

コード、テスト、コメント、コミットログへ同じ説明が重複すると、実装変更後に説明だけが古くなる。一方で、すべてをコードだけで表現すると、変更理由や却下した代替案が失われる。

コミット前に品質を確認し、品質を満たした変更だけへ理由を記録してコミットする順序も再現可能にする必要がある。

## Options

1. レビュー時の注意事項として文書だけに残す。
2. 汎用lint製品を追加し、設定で近似する。
3. リポジトリ固有の小さな検証器とGit hookで情報配置を検査する。

## Decision

選択肢3を採用する。

- プロダクションコードはHowを、名前、型、制御構造として表す。
- テストコードはWhatを、観測可能な振る舞いを表すテスト名とassertionとして表す。
- コミットログはWhyを、本文の`Why:`段落として表す。
- コードコメントはWhy notを、`WHY-NOT:`接頭辞付きで表す。

pre-commit hookはコミットログ以外の規約と全品質ゲートを検証する。commit-msg hookは`Why:`だけを検証する。CIもpre-commitと同じ検証スクリプトを実行する。

## Why not

- 文書だけでは適用漏れを検出できないため、選択肢1は採用しない。
- この原則に必要な検査は限定的であり、追加ランタイムと設定を導入する便益が小さいため、選択肢2は採用しない。
- コメントが不要なコードへ形式的なコメントを追加させない。コメントが存在する場合だけ`WHY-NOT:`を要求する。

## Consequences

- コミットには必ず理由が残る。
- 曖昧なテスト名と処理内容を言い換えるコメントをコミット前に拒否できる。
- pre-commitは全テストとE2Eを実行するため時間がかかるが、CIとの判定差を抑えられる。
